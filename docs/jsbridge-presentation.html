概念

JSBridge：Web 與原生 App 的通訊橋樑

Web

網頁（WebView）

跑在 App 內嵌瀏覽器，用 JavaScript 呼叫／接收訊息。

  • 呼叫原生能力（掃碼、取使用者…）
  • 訂閱 App 推播事件
Method →
JSBridge 統一訊息通道
← Event
Native

iOS／Android App

提供原生能力，註冊處理並可主動通知網頁。

  • 實作掃碼、導頁、權限等
  • 推播事件給 Web（如收藏更新）
Method · Web → App 網頁「請 App 做事」：例如掃碼、關 WebView、設標題。需要結果時會帶 requestId 等待回傳。
Event · App → Web App「主動通知網頁」：例如收藏已更新、請 Web 開 dialog。Web 用 onEvent 訂閱。
痛點 → 提案

模組化 SDK：減少三方溝通、跨專案可共用

以前

各自實作，無法重用

  • 每個專案各自做 Bridge，文件分散難管理
  • Web／iOS／Android method／event 名稱容易不一致
  • 多一個功能，就要反覆核對名稱、欄位與回傳
  • 文件、sample、手抄 wire 容易造成 bug
目標

規格驅動：一次定義，套件重複使用

  • 共用方法進 SDK、專案差異進專案套件
  • 以規格 JSON 為唯一來源 → codegen 產出三端 method／event 名稱
  • 前端呼叫封裝介面；App 只實作業務 Handler
  • 減少手抄 wire 的錯誤
預期效益

模組化，減少三方溝通成本

減少三方會議

以規格為準，不必每加功能或是開新專案就開會對欄位、對字串。

可重複使用

掃碼、導頁、語系等重複的功能組成共用模組；新專案安裝套件即可重用，不必重寫 Bridge。

減少不一致

三端同版本號發版 + 禁止手打程式碼，降低「Web 有、App 沒有」的問題 與 跨團隊溝通來回。

可量化指標

新 method 從「三方各自開發、反覆對規格」變成「改規格 + codegen + 各端實作業務」；跨平台字串 bug、文件過期、sample 複製錯誤，以及為對齊而開的會議次數應明顯減少。

架構

三層模組，職責清楚、可重複組合

共用 SDK
專案套件
產品端
{projectId}-front／iOS／Android — 只安裝套件、呼叫／註冊業務；不發布專案套件、不手動修改 generated

模組邊界清楚 → Web／iOS／Android 各做各的，靠規格對齊，不必反覆三方對字串。

使用方式 · Web

安裝專案套件（或直接安裝 SDK）

# 有專案套件（建議） pnpm add @omniguider/nmmba-bridge-contract # 無專案套件 pnpm add @omniguider/jsbridge-sdk
import { createBridge, BridgeMethod } from "@omniguider/nmmba-bridge-contract"; const bridge = createBridge({ debug: import.meta.env.DEV, mock: import.meta.env.DEV ? { "user.getInfo": () => ({ uuid: "dev" }), } : false, }); await bridge.user.getInfo(); bridge.navigation.setHeaderTitle("背包");
重點

前端職責變單純

  • 使用產生的 method／event 名稱，不要手抄字串
  • 本機可用 mock，不必綁定 App
  • 只裝專案套件就會一併帶入共用 SDK
  • 不要在前端 repo 發布專案套件
使用方式 · iOS／Android

安裝 Host 套件，只實作業務邏輯

iOS · Bitbucket + SPM

OmniguiderBridgeHost

import OmniguiderBridgeKit // 或 NmmbaBridgeContract let bridge = OmniguiderBridgeHost() bridge.install(on: configuration) bridge.registerSend(…) { /* 業務 */ }

Tag：vX.Y.Z／專案 {id}-vX.Y.Z

Android · Reposilite Maven

只裝專案套件 AAR

implementation( "com.omniguider:nmmba-bridge-contract:…" ) // api → kit host.registerSend(…) { /* 業務 */ } host.emitEvent(…)

禁止用 git include，也禁止複製 generated 檔

運作原理

兩種方向：Method 與 Event

通訊通道：iOS omniguiderBridge · Android OmniguiderBridge · 回傳 window.onOmniguiderBridgeMessage

實際流程

以 QR Code 掃描為例，一顆按鈕走完可追蹤的完整流程

  1. 1 Web 前端發起標準 Bridge request
  2. 2 iOS App 收到指定 Handler
  3. 3 App 開啟原生相機／掃描功能
  4. 4 掃描後依約定格式回傳結果
  5. 5 前端收到結果並更新畫面

AI 輔助落地

AI 在本專案做了什麼

盤點

收斂散落規格

  • 分析 HHApp 等既有專案的 ClickUp 文件
  • 掃描手寫 wire 與 sample
  • 整理共用 method／event 與專案專屬 API（如 nmmba）
規格

建立 SSOT 與架構

  • 產出 bridge.catalog.json／bridge.project.json
  • 定義 SDK、專案套件、產品端三層職責
  • method／event 以 JSON 為唯一來源（SSOT）
產出

codegen 與流程自動化

  • 自動產生 Web／iOS／Android 的 method／event 名稱
  • 產出 App 端 Bridge 初始化與註冊範本
  • Cursor skills（codegen／release／sync）串起發版流程

人工負責：業務邏輯實作、規格審核、發版決策 · AI 負責：盤點、對齊、重複性產出

總結

規格一次定義，三端對齊、模組可重用

核心做法
  • 規格 JSON 為 SSOT（catalog + bridge.project.json）
  • 共用進 SDK、專案差異進專案套件
  • 改規格 → codegen → 發版 → 產品端更新版號
  • Web 呼叫／訂閱，App 註冊業務，不手打 wire 字串
帶來改變
  • 少三方會議、少對欄位與字串
  • 掃碼、導頁等能力跨專案重用
  • 三端同版本號發版，降低不一致
  • AI 協助盤點規格、codegen 與發版流程
